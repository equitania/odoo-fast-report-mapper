## Summary

Phase 1.1 fixed seven correctness bugs (BUG-01 through BUG-07). The fixes are directionally correct and the new test suite is substantial. However, three new or pre-existing critical defects remain in the changed regions: a `TypeError` crash in `Report.add_dependencies()` when `_dependencies` is `False`, a missing null-guard in `add_field_to_dictionary()` that can crash or silently inject an empty-string dependency, and an empty-modules string bug that injects `""` into every exported dependency list. Four warnings cover: a test that skirts the `add_dependencies` crash instead of testing it, inconsistent `browse()` call semantics, redundant `get_primary_lang` in `resolve_attachment_value`, and the non-hermetic `_collect_calculated_fields` strips-spaces test.

## Critical Issues

### CR-01: `Report.add_dependencies()` crashes when `_dependencies` is `False`

**File:** `odoo_fast_report_mapper/_report.py:150`

**Issue:** The default value for `dependencies` (and therefore `self._dependencies`) is `False` (not `[]`). `add_dependencies` executes `self._dependencies = self._dependencies + dependency_list`. When `_dependencies` is `False`, `False + ["sale"]` raises `TypeError: unsupported operand type(s) for +: 'bool' and 'list'`. This crash occurs in any call path where `Report` is constructed without an explicit `dependencies` argument (e.g., the EqReport-style construction used by many callers) and `add_dependencies` is later called.

The test suite acknowledges the issue in a comment at `tests/test_report.py:37` ("Uses `dependencies=[]` (not False) so that `add_dependencies` works correctly") but does not test the crash path, and does not fix it.

**Fix:**
```python
def add_dependencies(self, dependency_list: list):
    # Guard: treat False / None as empty list before concatenation
    existing = self._dependencies if isinstance(self._dependencies, list) else []
    self._dependencies = existing + dependency_list
    self._dependencies = list(set(self._dependencies))
```

### CR-02: `add_field_to_dictionary()` calls `.modules` on an unguarded `browse()` result

**File:** `odoo_fast_report_mapper/_connection.py:668-670`

**Issue:** `field_id = IR_FIELDS.search(...)` can return an empty list. The code then calls `IR_FIELDS.browse(field_id)` unconditionally (line 669), followed by `field_obj.modules.replace(...)` (line 670). In odoorpc-toolbox a `browse([])` returns an empty record-set proxy; accessing `.modules` on it raises `AttributeError` or returns a falsy non-string value depending on the version. There is no guard between the search and the browse. This is reachable whenever Odoo does not recognize the field (e.g., a computed field without a corresponding `ir.model.fields` entry), causing the entire `collect_report_entries` run to crash mid-export and lose already-accumulated data.

**Fix:**
```python
field_id = IR_FIELDS.search([("model_id", "=", model_id[0]), ("name", "=", field_name)])
if not field_id:
    logger.debug(f"Field '{field_name}' on '{model_name}' not found in ir.model.fields — skipping dependency")
    return data_dictionary
field_obj = IR_FIELDS.browse(field_id)
modules_dependencies = field_obj.modules.replace(" ", "").split(",")
```

### CR-03: Empty `modules` string injects `""` into exported dependency lists

**File:** `odoo_fast_report_mapper/_connection.py:670`

**Issue:** `ir.model.fields.modules` is frequently an empty string `""` (fields native to the base module have no module annotation). `"".replace(" ", "").split(",")` produces `[""]` — a list containing one empty string. This empty string is then appended to `data_dictionary[report_id]["dependencies"]` and survives the `list(set(...))` deduplication. The result: every exported YAML report that has at least one base-module field gains `""` in its `dependencies` list. When that YAML is later imported and `create_report_object_from_yaml_object` feeds the list to `Report`, `check_dependencies(["", "sale"])` calls `check_module("")`, issuing a pointless RPC query.

**Fix:**
```python
raw_modules = field_obj.modules.replace(" ", "").split(",")
modules_dependencies = [m for m in raw_modules if m]   # discard empty strings
if not modules_dependencies:
    return data_dictionary
```

## Warnings

### WR-01: Test skirts `add_dependencies(False)` crash instead of covering it

**File:** `tests/test_report.py:37`

**Issue:** The `minimal_report` fixture explicitly uses `dependencies=[]` with the inline comment "not False — so that `add_dependencies` works correctly." This documents the bug but deliberately avoids exercising the broken code path, leaving CR-01 invisible to the test suite. Any regression that restores `False` as the default will not be caught.

**Fix:** Add a dedicated test:
```python
def test_add_dependencies_when_default_false():
    """Report constructed with default dependencies=False must not crash."""
    report = _make_report()   # dependencies defaults to False
    report.add_dependencies(["sale"])
    assert report._dependencies == ["sale"]
```

### WR-02: `add_field_to_dictionary()` re-initializes `IR_FIELDS` and `IR_MODEL` on every call

**File:** `odoo_fast_report_mapper/_connection.py:662-663`

**Issue:** `add_field_to_dictionary` is called inside the `for field_id in progress_bar(...)` loop in `collect_report_entries`. It re-fetches `IR_FIELDS` and `IR_MODEL` via `self.connection.env[...]` on every invocation. While not a correctness bug, when combined with the missing `field_id` null-guard (CR-02), a re-raise from line 669-670 would surface as an uncaught exception in an inner loop that has no exception handler in `collect_report_entries`, aborting the entire collection. The two issues together amplify the crash radius.

**Fix:** Hoist the environment lookups to the top of `collect_report_entries` (or at least above the per-field loop) so they execute once, and add the CR-02 guard.

### WR-03: `_search_report_v13` and `_search_report` use falsy check for `company_id` — `0` silently omits company filter

**File:** `odoo_fast_report_mapper/_connection.py:185, 196`

**Issue:** Both search helpers guard the company domain with `if company_id:`. Odoo company IDs are database serial integers; `0` is not a valid company ID in practice. However, the Odoo ORM occasionally surfaces `company_id = False` (no company), and the falsy guard correctly collapses that. The pre-existing concern is that the guard also silently drops the company filter for the numeric value `0` if it were ever passed. This is a latent correctness risk rather than an active bug, but it was present before phase 1.1 and not addressed.

**Fix:** Use an explicit `is not None` check for clarity:
```python
if company_id is not None and company_id is not False:
    domain += ["|", ("company_id", "=", company_id), ("company_id", "=", False)]
```

### WR-04: `resolve_attachment_value` calls `get_primary_lang()` then indexes the result redundantly

**File:** `odoo_fast_report_mapper/_lang_utils.py:119-121`

**Issue:** The fallback chain at lines 119-121 is:
```python
primary = get_primary_lang(attachment)
if primary in attachment:
    return attachment[primary]
return next(iter(attachment.values()))
```
`get_primary_lang(attachment)` by contract always returns a key that is already in `attachment` (it returns `next(iter(name_dict))` at worst, which is always a valid key). Therefore the `if primary in attachment:` guard is always `True` and the `next(iter(...))` fallback is dead code. This creates a false impression that the last line is reachable, making the fallback contract harder to audit.

**Fix:**
```python
# get_primary_lang always returns a valid key — no additional guard needed
return attachment[get_primary_lang(attachment)]
```
